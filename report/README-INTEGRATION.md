# Отчёт по товарообороту арендатора — пакет для интеграции

Версия: 09.11.2026 (заменяет пакет от 09.09.2026) · Заказчик: отдел аренды Tashkent City Mall (Hyper Partners)
Контакт по методологии: Олег (группа постоянных улучшений).

## 1. Что это

Отчёт по одному арендатору на трёх листах A3 (альбомная ориентация):

| Лист | Содержание |
|---|---|
| 1. Арендатор и его торговля | оборот по месяцам, скользящий год, ТО на м² против медианы базы, сезонный профиль, матрица год × месяц, итоги по годам |
| 2. Деньги ТРЦ, позиция и сроки | OCR по месяцам, матрица ТО на м² × OCR, ставка: план физибилити и факт, доход ТРЦ с м², календарь договора, условия, вывод и рекомендации |
| 3. Сравнение с коллегами | фильтры (менеджер, сегмент, категория, подкатегория, под-подкатегория, месяц, годы), режимы «месяц к месяцу» / «с начала года», 4 графика по брендам и годам: ТО, ТО на м², средний чек, превышение ТО над порогом договора |

Файл `tenant-report.html` — самодостаточный: открывается двойным кликом,
работает без интернета, «Печать / PDF» выдаёт ровно три листа A3.
**Внешних запросов ноль** (ни CDN, ни шрифтов, ни аналитики). При размещении
на сервере это требование сохранить: отчёт содержит коммерческую тайну
(обороты, ставки), утечек через сторонние ресурсы быть не должно.

Сейчас внутри вымышленные демо-данные (5 арендаторов + пул молла). Структура
классификатора реальная. Задача интеграции: заменить демо-данные выгрузкой из БД.

### Что изменилось с версии 09.09
- Печать на **A3** вместо A4, листов три вместо двух.
- Новый модуль `compare.js` — лист 3 и его контракт данных (раздел 3.5).
- База сравнения теперь **строго своя**: та же подкатегория и тот же сегмент (раздел 3.6).
- Новые графики и оформление на листах 1–2 (логика расчётов не менялась,
  контракты 3.1–3.4 прежние).

`overflow`, `render`). Их правят вручную в самом файле.

## 3. Контракты данных (что генерировать из БД)

### 3.1 `categories.js` — классификатор

```js
var SEG_ORDER = ['Mass','Upper Mass','Contemporary','Premium','Bridge Luxury','Luxury'];
var CAT_CODE = { "Fashion & Accessories": "FAS", ... };   // 9 категорий
var TAXONOMY = [
  "Contemporary|Fashion & Accessories|Apparel|Womenswear",  // сегмент|категория|подкат|под-подкат
  ...                                                        // одна строка = один арендатор
];
```
Источник в БД: справочник арендаторов с 4 уровнями классификации.
Значения уровней должны совпадать со строками в `ocr-benchmarks.js` /
`to-benchmarks.js` (ключи — названия подкатегорий, точное совпадение).

### 3.2 `data.js` — арендаторы и пул

**BRANDS** — арендаторы, доступные в выпадающем списке отчёта:
```js
{ id:'meridian',            // латиница, уникальный
  brand:'CAFE MERIDIAN',
  cat:'Food & Beverage', catCode:'FNB',
  seg:'Contemporary', sub:'Cafés', sub2:'Coffee shop / patisserie',
  area:148,                 // м²
  floor:'3 этаж', unit:'U3-007',
  rows:[ {y:2024, m:2, to:54123}, ... ],  // помесячный оборот, $;
                                          // месяц НЕ ПОДАН → to:null (не 0!)
  check:9.2, checkTrend:0.006             // демо среднего чека — см. 3.5
}
```
В демо `rows` генерируются функцией `buildSeries` — при интеграции удалить
генератор и подставлять готовые ряды из БД. Поля `start/n/baseM2/trend/season/
seed/note` — только для генерации демо, в проде не нужны.

**DEAL[id]** — договор арендатора:
```js
{ contract:'01.04.2022 — 31.03.2027',   // строго ДД.ММ.ГГГГ — ДД.ММ.ГГГГ (парсится)
  endsIn:7,                              // мес. до окончания
  type:'фикс $/м²',
  rent:60, opex:10, mkt:4,               // $/м² в месяц: аренда, эксплуатация, маркетинг
  indexation:'5% в год', deposit:'2 мес. аренды',
  debt:18400, overdueDays:34, latePayments:3,
  zoneTraffic:118000,                    // трафик этажа, чел./мес (пока справочно)
  issues:['...'],                        // замечания эксплуатации (пока не выводятся)
  altRate:72, altBrand:'...', altReady:'...',   // ставка/кандидат замены
  fitOut:12000, vacancyMonths:2,         // цена ротации
  offerPct:12, offerMinFix:45 }
```

**MALL** — пул ВСЕХ арендаторов молла (база сравнения, медианы, матрица ТО × OCR):
```js
{ id:'m1', brand:'ARMO',
  cat:'FNB', catName:'Food & Beverage', seg:'Mass',
  sub:'QSR / Food court', sub2:'Fast food',
  area:120,
  m2:355.2,        // средний ТО на м² в месяц за последние 12 мес., $
  occ:16.5,        // OCR, % (платежи/оборот без НДС × 100)
  toYear:511488,   // оборот за 12 мес., $
  growth:4.2,      // рост оборота г/г, %
  season:[93,88,101,...],  // 12 индексов сезонности, среднее = 100
  rentM2:47.8 }    // доход ТРЦ с м² в месяц, $
```
В демо MALL генерируется из TAXONOMY со случайной экономикой — генератор
удалить, заполнять из БД. `season` считать по помесячным оборотам:
средний оборот месяца ÷ средний месяц × 100 (за последние 12 мес.).

### 3.3 `rates-plan.js` — ставки физибилити и факт

```js
var PLAN_YEAR = 2022;        // год финансовой модели
var PLAN_INDEX = 0.05;       // индексация модели, в год
var PLAN_TERM = 5;           // горизонт, лет
var PLAN_RATE = { FNB: { '-1':26, '1':70, '2':54, '3':44, '4':52 }, ... };
                             // базовая аренда $/м²/мес по категории × этажу (демо!)
```
Заменить `PLAN_RATE` реальными ставками физибилити. Если в вашей модели другой
разрез (по зоне/юниту, не категория×этаж) — переписать `planRate()` и
`planLadder()`, интерфейс на выходе сохранить: `planLadder(b,d)` возвращает
`[{y:1..5, cal:год, plan:$}]`.

**Фактические ставки по годам** — сейчас демо-функция `factLadder()`
восстанавливает историю от текущей ставки темпом `FACT_INDEX_DEMO = 3%`.
Заменить чтением реальной истории ставок из БД:
`factLadder(d, curY)` → `[{y:1, fact:52}, {y:2, fact:54}, ...]`.

### 3.4 НДС — обязательно проверить

`ocr-benchmarks.js`:
```js
var VAT_RATE = 0.12;
var TO_INCLUDES_VAT = false;   // true, если обороты в БД хранятся С НДС
```
Все OCR считаются от оборота БЕЗ НДС (`netTO()`). Если выгрузка с НДС —
переключить флаг, пересчёт по листам 1–2 автоматический. Если поставить
неправильно, ВСЕ проценты нагрузки уедут на ~11% — сверьте с бухгалтерией.
Лист 3 («превышение ТО без НДС») ожидает обороты уже без НДС — см. 3.5.

### 3.5 `compare.js` — данные листа 3 (НОВОЕ)

Листу 3 нужны помесячные ряды по ВСЕМ арендаторам пула, а не только годовые итоги.
Сейчас они генерируются в `compare.js` (`CMP_POOL`, `cmpMe`) — заменить данными из БД.

Нужно для каждого арендатора пула (элемент `CMP_POOL`):
```js
{ id:'m1', brand:'ARMO',
  cat:'FNB', catName:'Food & Beverage', seg:'Mass', sub:'QSR / Food court', sub2:'Fast food',
  area:120,                         // м²
  mgr:'Каримов Р.',                 // ответственный менеджер отдела аренды
  rows:[ { y:2024, m:1,
           to:42110,                // оборот за месяц БЕЗ НДС, $ (не подан → строку не передавать)
           chk:11.4,                // средний чек за месяц, $ (= оборот ÷ число чеков)
           ex:0 },                  // превышение оборота над месячным порогом % аренды, $ (≥ 0)
         ... ],
  me:false }
```
- `ex` = max(0, оборот без НДС − месячный порог процентной аренды по договору).
  Если удобнее, передайте порог (`bpMonth`), а `ex` посчитайте в генераторе.
- История — минимум 3 календарных года (фильтр «Годы»), до последнего закрытого месяца.
- `CMP_LAST` — последний месяц с данными; `CMP_MGRS` — список менеджеров для фильтра.
- Для отчётного арендатора (`cmpMe(b)`) те же поля: его `to` уже берётся из `BRANDS.rows`,
  дополнить реальными `chk` и `ex` (сейчас демо: чек из `check/checkTrend`, порог = 95% среднего).

Расчёт показателей (менять не нужно, для сверки):
- «Месяц к месяцу»: значение выбранного месяца в каждом выбранном году.
- «С начала года»: сумма январь…выбранный месяц; год показывается, только если поданы все месяцы.
- ТО на м² в режиме «с начала года» — среднее за месяц; средний чек — оборот ÷ сумма чеков.
- % над столбцами — последний выбранный год к предыдущему; звезда — бренд с наибольшим приростом.

### 3.6 База сравнения (листы 1–2)

База — арендаторы той же **подкатегории** (3-й уровень) и того же **сегмента**.
Соседние сегменты и уровни выше не подмешиваются. При n < 8 в шапке появляется
«узкая выборка», база не меняется. Если в группе 0 арендаторов, берётся ближайшая
группа с n ≥ 5, и об этом пишется в подвале листа 2.

## 4. Два сценария серверной интеграции

**А. Рекомендуемый — статика + генерация data-файлов по расписанию.**
Джоб (cron/planner) раз в сутки/месяц выгружает из БД и генерирует файлы
(`categories.js`, `data.js`, `rates-plan.js` и блок данных `compare.js`) по контрактам
выше, затем `python build.py` → готовый `tenant-report.html` кладётся на веб-сервер.
Плюсы: ноль рантайм-зависимостей, отчёт работает даже при недоступной БД,
можно рассылать файлом.

**Б. Динамика — эндпоинт вместо файлов.**
Раздавать модульный вариант, где `<script src="data.js">` заменён на
`<script src="/api/tenant-report/data.js">` — эндпоинт отдаёт тот же JS
по контракту (Content-Type: application/javascript). Логика отчёта не меняется.
Авторизацию и доступ — на вашей стороне (данные — коммерческая тайна).

В обоих случаях НЕ редактировать `final.js`/`charts.js` под данные —
если контракт неудобен, лучше согласовать изменение контракта с Олегом.

## 5. Что где проверить после подключения реальных данных

1. Открыть отчёт, выбрать 3–4 арендаторов разных категорий: «Печать / PDF» —
   ровно 3 листа A3, без наложений подписей.
2. KPI «OCR арендатора» = (rent+opex+mkt)×area×мес ÷ оборот периода без НДС.
3. Пилюля «база: … · N арендаторов» в шапке листа 1; при N < 8 — «узкая выборка».
4. Месяц без оборота отображается прочерком (не нулём) и рвёт линии графиков.
5. График «Ставка: план и факт»: план года N = base × 1.05^(годСтарта+N−1−2022).
6. Лист 3: по умолчанию — категория и подкатегория арендатора, последний месяц
   с его оборотом и год до него; отчётный арендатор выделен медным на всех графиках.
7. Поиск по странице: строк «undefined» и «NaN» быть не должно.

## 6. Известные ограничения (осознанные, не баги)

- Сезонность арендатора — последние 12 мес.; сезонность базы — типичный год
  пула. С реальными помесячными данными пула стоит привести к одному периоду.
- Пропущенный месяц выпадает из окна сезонности (не занимает пустую позицию).
- Бенчмарки OCR/ТО заданы на уровне подкатегорий; под-подкатегории не
  дифференцируются (нет источников).
- Лист 3: при очень широкой выборке (40+ брендов × 3 года) часть брендов не
  помещается — показываются первые по убыванию, в подзаголовке «показаны N из M»;
  единичные цифры могут касаться друг друга.
- Режим «Крупнее на 15/30%» местами не укладывается в лист (запасной режим для экрана).
- `zoneTraffic` и `issues` в DEAL зарезервированы, в текущей версии не выводятся.
